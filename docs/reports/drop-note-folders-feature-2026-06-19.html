主持：主 Claude · 参会：product-manager + manager-mathieu (Product & Eng VP) · 阶段：仅头脑风暴，未写任何代码 · 产品归属：drop-mic / 代码执行：techlead-jose

🎯 一句话结论

给 drop-note 加一层 Folders（文件夹/容器）：每个 item 单归属一个 folder（move 语义，像邮件文件夹）。 左侧导航的 Tags section 整体换成 Folders，顶部 tags 过滤器保留——彻底消除你说的"左边和顶部 tags 重复"。 指派方式两通道：kebab 菜单（移动端一等公民）+ 桌面端原生拖拽（你点名要的交互，已确认可低成本实现）。 没选 folder = 虚拟的 All Items 视图，不建真实的 ALL 文件夹。

三方一致。预想的几个分歧（单/多归属、是否做拖拽、排期）经两轮挑战后全部收敛。下方"🟡 需要你拍板"列出仅剩的 3 个真正决策。

🧭 核心心智模型 — Folder vs Tag 分工

这是整个设计的地基：两条信息轴彻底分开，不再重叠。和 Bear / Notion / Linear 的做法一致。

维度Folder（新增）Tag（保留）
语义它住在哪里（容器）它是什么（属性标签）
归属数量一个 item 只能在 1 个 folder一个 item 可有 多个 tags
谁来赋值只有用户手动AI auto-tag + 用户手动
导航入口只在左侧导航只在顶部过滤条
典型例子Sports · Next week · Work#article · #video · #urgent

👉 "一篇文章既想放 Sports 又想放 To-read" 怎么办？用 tag 解决——folder 是唯一主容器，tag 是横切标签。这条规则需要在 UI 上对用户讲清楚。

🗄 数据模型草案

改动极小：新增 1 张表 + items 加 1 个 nullable 外键。现有 tags / item_tags 零改动，AI pipeline 零感知，存量数据零迁移。

-- 新建 folders 表
folders
├── id          uuid  PK
├── user_id     uuid  FK → auth.users
├── name        text  NOT NULL
├── position    int   DEFAULT 0          -- 支持手动排序
├── created_at  timestamptz
└── UNIQUE(user_id, lower(name))         -- per-user 唯一、大小写不敏感（与 tags 表一致）

-- items 表加一列
items.folder_id  uuid  FK → folders(id) ON DELETE SET NULL
                                          -- NULL = 未分类 → 归入虚拟 All Items
-- 复合索引 (user_id, folder_id)
⚠️ 安全高发区（Jose 必须处理）：RLS。folders 表加 user_id = auth.uid() policy；同时 items.folder_id 的 insert/update policy 要加 exists 子查询，**禁止把 item 指派到别人的 folder**。这是最容易漏的跨用户漏洞。

🖱 交互设计（UX）

① 给单个 card 指派 folder

  • 主交互：card 右上角 ... kebab 菜单 → "Move to folder" → inline 下拉选择
  • 移动端：tap kebab 触发，功能完全等价，无残缺
  • 批量：多选后顶部 action bar 出 "Move to" 按钮

❌ 不用右键 context menu（移动端不可用）

② 桌面端拖拽（你点名要的）

  • 用浏览器原生 HTML5 DnD，不引第三方库
  • 拖起 item → 左侧 folder 高亮成 drop zone
  • 放下 → move 进去 + toast "Moved to Sports" + 乐观更新计数
  • 复用和 kebab 菜单同一个 PATCH /api/items/:id

③ 移动端 fallback

原生 HTML5 拖拽在触屏上天然不触发 → 移动端自动走 kebab 菜单，无需维护两套逻辑。左侧导航在移动端是抽屉，tap folder 进入该视图。

✅ 关键技术确认（Mathieu 二轮诚实下修）："拖拽 = 要引 @dnd-kit（+20-30KB、包整个布局的 context、hydration 风险）"这个前提是错的。原生 HTML5 DnD 零 bundle、零 context、不改 hydration 边界。成本从原估 +1.5~2d 下修到 +0.5~1d。所以拖拽进 v1 是合理 scope，不是过度工程。

📦 v1 Scope 边界

v1 要做

  • 创建 / 重命名 / 删除 folder
  • folder 手动排序（position 字段）
  • item 单归属指派（kebab 菜单）
  • 桌面端原生拖拽指派
  • 左侧导航 Tags section → 换成 Folders section
  • 虚拟 All Items 视图（顶部固定，不可删）
  • 顶部 tags 过滤器保留

砍到 v2 / 以后

  • 嵌套 / 子文件夹
  • folder 颜色 / 图标
  • GTD 型 folder（截止日 / 提醒 / "清空清单"）
  • Smart folder（按 tag 规则自动归类）
  • folder 分享（另一套 auth + RLS）
  • 多归属（明确不做，用 tag 替代该需求）

关于 "Next week" 这类计划型 folder：v1 不区分"主题型 vs 计划型"，统一成一种灵活 folder——用户自定义语义即可。里面积压旧 item 是使用习惯问题，不是数据模型问题。未来可加 type 字段支持 GTD 动作，但 v1 砍掉（beta resist scope creep）。

🟡 需要 Jason 拍板（3 个）

下面是三方收敛后仍需你定的真正决策。每条给了我们的推荐。

1. 单归属 vs 多归属 —— 一个 item 只能在 1 个 folder，还是能同时在多个？
📌 我们一致推荐：单归属（move 语义）。更符合你"放进 sports 里去"的说法，心智清晰，和 tags 分工不重叠，工程最简。代价：想让一个 item 同时归两类，得用 tag 而不是第二个 folder。这条会约束整个数据模型，请确认你接受。
2. 桌面端拖拽 —— v1 就做，还是先只做菜单、拖拽放 v2？
📌 推荐：v1 就做（原生 HTML5，desktop-only，+0.5~1d）。这是你点名要的交互，且确认了低成本无架构债。移动端走 kebab 菜单。若你想更快见到 folder 雏形，也可选择 v1 先菜单、拖拽 v2——但我们认为没必要砍。
3. 排期 —— Folder 现在就让 Jose 开做，还是先把 Sentry/监控并行铺好？
📌 推荐：Sentry 在 Folder 开发期间并行接入（2~4h），public launch 前必须就位；Folder v1 可以现在就启动，不必卡 beta。两者不冲突。
